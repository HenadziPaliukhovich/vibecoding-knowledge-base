Настройка локального окружения

01

Выполняется один раз на новой машине. Дальше — только запуск claude в папке проекта.

01

Установи Node.js и Claude Code CLI

Claude Code — это Node-пакет, ставится глобально через npm.

node -v || brew install node
npm install -g @anthropic-ai/claude-code
claude --version
02

Авторизуйся

Через Claude аккаунт (Pro/Max) или API-ключ Anthropic.

claude
# в интерактивном режиме появится ссылка для входа в браузере
# либо задай переменную окружения:
export ANTHROPIC_API_KEY="sk-ant-..."
03

Поставь вспомогательные CLI

Claude эффективнее работает с внешними сервисами через их официальные CLI, а не «вручную» через API.

brew install gh          # GitHub
gh auth login
brew install awscli       # если используешь AWS
brew install google-cloud-sdk   # если используешь GCP
04

Инициализируй проект

Команда /init сканирует структуру репозитория и создаёт стартовый CLAUDE.md, который дальше нужно вручную сократить и уточнить.

cd my-project
claude
/init
/context   # проверить, что CLAUDE.md действительно загрузился
05

Режимы доступа и sandbox

У Claude Code три режима выполнения — выбирай по риску задачи, а не один режим на всё.

  • Plan mode — читаешь и уточняешь, ничего не меняется
  • Manual approvals — подтверждаешь Edit и Bash по одному
  • Auto-accept — безопасные действия идут быстрее, но только в изолированной среде
/permissions
# добавь в allowlist: npm run lint, npm test, git commit *, git diff
/sandbox   # включить изоляцию файловой системы и сети
/model     # переключить модель под задачу
06

Личные настройки vs командные

Три уровня памяти помогают не смешивать личные привычки, правила команды и локальные заметки.

  • ./CLAUDE.md — общие правила проекта, коммитится в git
  • ./CLAUDE.local.md — твои временные заметки, в .gitignore
  • ~/.claude/CLAUDE.md — глобальные личные правила для всех проектов
07

Зафиксируй локальное окружение

Лучше работать в воспроизводимой среде: одинаковые версии Node, Python и системных CLI дают предсказуемый результат и тебе, и Claude.

# .devcontainer/devcontainer.json
{
  "image": "node:20",
  "postCreateCommand": "npm install -g @anthropic-ai/claude-code && npm ci",
  "remoteEnv": { "ANTHROPIC_API_KEY": "${localEnv:ANTHROPIC_API_KEY}" }
}

# быстрый изолированный запуск через Docker
docker run --rm -it -v $(pwd):/work -w /work node:20 bash -lc   "npm install -g @anthropic-ai/claude-code && claude"

Рабочий цикл: 4 фазы

02

Главная ошибка — дать Claude сразу писать код. Разделяй исследование, план и реализацию, иначе получишь решение неправильной задачи.

1

Explore — план-режим

Shift+Tab до статуса «plan mode on». Claude читает код и отвечает на вопросы, ничего не меняя.

read /src/auth and understand how we handle sessions and login.
also look at how we manage environment variables for secrets.
2

Plan — попроси детальный план

План можно открыть в редакторе через Ctrl+G и вручную проаннотировать: «используй PATCH, не PUT», «добавь created_at с NOW()».

I want to add Google OAuth. What files need to change?
What's the session flow? Create a plan.

# после правок в плане:
address all notes, don't implement yet
3

Implement — с проверкой

Выходишь из план-режима и даёшь Claude критерий успеха: тесты, скрипт, скриншот.

implement the OAuth flow from your plan. write tests for the
callback handler, run the test suite and fix any failures.
4

Commit — с описанием

Не оставляй сообщения коммитов на потом — проси их сразу.

commit with a descriptive message and open a PR

Verification loop

Главное правило из практики Anthropic: не проси «сделай», проси «сделай и проверь». Тест, build, screenshot diff или точный acceptance-check превращают Claude из генератора текста в исполнителя с критерием завершения.

implement the change, run tests, fix failures,
and summarize what you verified before stopping.

Checkpoint и откат

Если Claude ушел̈ не туда, не спорь 20 сообщений подряд. Используй быстрый откат к прошлому checkpoint или очищай сессию и заходи с более точным промптом.

Esc Esc      # открыть checkpoints
/rewind      # вернуться к более раннему состоянию
/clear       # начать свежую сессию для другой задачи

Когда план-режим — избыточен

Если правку можно описать одним предложением (опечатка, лог, переименование переменной) — план не нужен, проси делать сразу. План оправдан, когда: неясен подход, меняется несколько файлов, или ты не знаком с этим кодом.

Как писать CLAUDE.md

03

CLAUDE.md читается в начале каждой сессии. Системный промпт Claude Code уже занимает часть «бюджета следования инструкциям» — раздутый файл означает, что важные правила потеряются в шуме.

✓ Включай

Bash-команды, которые Claude не угадает · стиль кода, отличающийся от дефолта · инструкции по тестам · repo-этикет (ветки, PR) · архитектурные решения · переменные окружения · неочевидные особенности проекта

✗ Исключай

Всё, что Claude выведет из кода сам · стандартные конвенции языка · подробную документацию API (дай ссылку) · часто меняющуюся информацию · длинные объяснения и туториалы · файл-за-файлом описание кодовой базы

Пример короткого корневого файла (реальная структура)

# CLAUDE.md

## Project
Monorepo managed with pnpm workspaces. Packages in packages/*.
Build: pnpm build. Test: pnpm test.

## Code style
- Use ES modules (import/export), not CommonJS (require)
- Destructure imports when possible: import { foo } from 'bar'

## Workflow
- Typecheck after a series of changes: pnpm typecheck
- Prefer running single tests, not the whole suite, for speed
- Use the simplest possible approach — no premature abstractions

## For domain-specific rules, see:
- Payments: read docs/payment-architecture.md first
- API conventions: src/api/CLAUDE.md

Прогрессивное раскрытие

Не вставляй целый документ в CLAUDE.md — это съедает лимит инструкций на каждой сессии. Вместо этого дай ссылку на файл, который Claude прочитает только при необходимости.

## Payments
When touching src/payments/, first read
docs/payment-architecture.md before editing.

Файлы по подпапкам

Claude подгружает CLAUDE.md от текущей рабочей директории вверх до корня. Правила для БД или API можно держать локально — они активируются только в нужной зоне.

src/persistence/CLAUDE.md   → правила БД
src/api/CLAUDE.md           → конвенции эндпоинтов
~/.claude/CLAUDE.md         → твои личные глобальные правила

Диагностика

Если Claude игнорирует правило — файл слишком длинный, и правило теряется в шуме; сократи его. Если Claude переспрашивает то, что уже написано в файле — формулировка неоднозначна. Если правило постоянно пропускается, выдели его одним словом «IMPORTANT», но не выделяй так много строк — тогда ничего не будет выделяться. Держи файл в git, чтобы команда могла его дополнять, и запускай /doctor для автоматических предложений по сокращению.

Управление контекстом

04

Качество ответов начинает падать задолго до лимита окна — многие практики согласны не превышать 60% заполнения на глаз. Автокомпакция срабатывает около 83% и теряет детали.

Document & Clear — базовый паттерн

Как только контекст «тяжелеет»: выгружаешь план и прогресс в markdown, чистишь сессию, начинаешь заново с чтением этого файла. Так ты сам решаешь, что переживёт очистку — а не автокомпакция.

# сохранить прогресс перед очисткой
Dump current plan and progress to PROGRESS.md,
including decisions made and files touched.

/clear

# новая сессия
Read PROGRESS.md and continue from where we left off.

Одна задача — одна сессия

«Сессия-помойка»: начал с одной задачи, спросил что-то не связанное, вернулся к первой — контекст забит нерелевантным. После двух неудачных исправлений одной и той же проблемы — очищай сессию и переформулируй промпт точнее, вместо продолжения спора.

  • /clear между несвязанными задачами
  • /compact Focus on the API changes для точечного сжатия
  • /btw для побочных вопросов, которые не должны расти в контексте

Субагенты для разведки

Исследование кода читает десятки файлов — весь этот объём съедает основной контекст. Субагент работает в отдельном окне и возвращает только summary.

Use subagents to investigate how our authentication system handles
token refresh, and whether we have any existing OAuth utilities I should reuse.

Хуки и проверка результата

05

CLAUDE.md — это советы, им следуют не всегда. Хуки — детерминированные скрипты, которые гарантируют действие каждый раз без исключений.

Автоформатирование после правок

PostToolUse-хук запускает Prettier или линтер сразу после Edit/Write, без остановки работы Claude.

{
  "hooks": {
    "PostToolUse": [{
      "matcher": "Edit|Write",
      "hooks": [{
        "type": "command",
        "command": "prettier --write \"$CLAUDE_FILE_PATHS\""
      }]
    }]
  }
}

Жёсткий запрет опасных команд

PreToolUse-хук с exit code 2 блокирует действие целиком — например, push в main или rm -rf.

Write a hook that blocks 'git push' directly to main
and suggests opening a PR instead.

Write a hook that blocks 'rm -rf' and suggests 'trash' instead.

Дай Claude способ себя проверить

Без проверяемого критерия «выглядит готово» — это единственный сигнал, и тогда ты сам становишься циклом проверки. Дай тест, сборку или скриншот для сравнения.

ДоПосле
implement a function that validates email addresseswrite a validateEmail function. example test cases: user@example.com is true, invalid is false. run the tests after implementing
make the dashboard look better[скриншот] implement this design. take a screenshot of the result and compare it to the original. list differences and fix them
the build is failingthe build fails with this error: [текст]. fix it and verify the build succeeds. address the root cause, don't suppress the error

Adversarial review — второе мнение

Свежий субагент видит только diff и критерий, а не ход рассуждений — поэтому оценивает результат честно.

Use a subagent to review the rate limiter diff against PLAN.md. Check that
every requirement is implemented, listed edge cases have tests, and nothing
outside the task's scope changed. Report gaps, not style preferences.

Что чем управлять

06

Не всё нужно запихивать в один CLAUDE.md. Качественная рабочая среда строится из мягких правил, жестких ограничений и контекста по требованию.

ИнструментКогда использоватьЧто хранить
CLAUDE.mdДля коротких правил, которые нужны почти в каждой сессииworkflow, стиль, команды, критерии проверки
HooksКогда правило должно выполняться всегдаформатирование, блокировки push в main, запрет опасных команд
SkillsКогда знание нужно не всегда, а по конкретной задачеdeploy, migrations, release, performance review
SubagentsКогда нужно изолировать исследование или ревьюauth audit, security review, diff review, docs pass

Как держать CLAUDE.md коротким

Пиши только то, что модель сама не выведет из кода. Хорошее правило проверяемо, кратко и, если что-то запрещает, сразу предлагает безопасную альтернативу.

Bad: don't use destructive commands.
Good: never run rm -rf; move files to Trash or ask first.

Skills вместо длинных простыней

Редкие, объёмные инструкции выноси в .claude/skills/. Тогда корневой CLAUDE.md останется компактным, а Claude прочитает детальный playbook только в нужный момент.

.claude/
  skills/
    deploy/SKILL.md
    db-migrations/SKILL.md
    code-review/SKILL.md

Автоматизация и масштаб

07

Когда базовый цикл работает, переноси повторяемые задачи в headless-команды, batch-режим и отдельные ревью-сессии.

Headless и CI

Для повторяемых задач удобен запуск без интерактивного UI. Это подходит для генерации описаний, проверки diff, миграции серии файлов и CI-задач.

claude -p "review the staged diff and list risks"   --output-format text

claude -p "summarize changes in this PR"   --output-format json

Fan-out и writer/reviewer

Одна сессия пишет, другая проверяет с нуля. Для серии однотипных файлов удобнее прогонять Claude циклом или через batch-подход с узким prompt scope.

for file in $(cat files.txt); do
  claude -p "migrate $file to the new API and report OK or FAIL"
done

Библиотека промптов

08

TDD-цикл

1. Write tests for the auth module using pytest.
TDD approach, no mock implementations.
2. Run the tests — they should all fail.
3. Commit the failing tests as a checkpoint.
4. Write the implementation. Do not modify
the tests. Keep going until all tests pass.

Интервью перед фичей

I want to build [описание]. Interview me in detail
using the AskUserQuestion tool. Ask about technical
implementation, UI/UX, edge cases, and tradeoffs.
Don't ask obvious questions. Keep interviewing until
we've covered everything, then write a spec to SPEC.md.

Исследование багов

Users report that login fails after session timeout.
Check the auth flow in src/auth/, especially token
refresh. Write a failing test that reproduces the
issue, then fix it.

Автономный batch-режим

for file in $(cat files.txt); do
  claude -p "Migrate $file from Python 2 to Python 3.
  Return OK or FAIL." \
    --allowedTools "Edit,Bash(git commit *)"
done

Writer / Reviewer

# Сессия A
Implement a rate limiter for our API endpoints

# Сессия B (свежий контекст)
Review the rate limiter in @src/middleware/rateLimiter.ts.
Look for edge cases, race conditions, and consistency
with existing middleware patterns.

Изучение чужого CLI

Use 'foo-cli-tool --help' to learn about foo tool,
then use it to solve A, B, C.

Личные заметки

10

Эта форма удобна только как черновик в текущем браузере. Всё, чем ты реально хочешь пользоваться на другой машине или после нового деплоя, должно жить в репозитории как файл.

Постоянные заметки — только через git

Храни личные playbook-заметки в artifacts/notes/, а проектные правила — в CLAUDE.md или .claude/skills/. Тогда знания будут переживать новый компьютер, очистку браузера и любой повторный деплой.

mkdir -p artifacts/notes
cat > artifacts/notes/debugging-session.md <<'EOF'
# Debugging session
- Symptom:
- Root cause:
- Fix:
- Verification:
EOF

git add artifacts/notes/debugging-session.md
git commit -m "Add debugging note"
git push
