Checklist to 100%

1

Shape the idea before opening the editor

10 min

Start with the problem and the smallest useful outcome — not screens or technologies. This stops Claude from guessing the product scope for you.

  • Problem: [who] struggles with [specific problem]
  • Smallest outcome: they can [one action] so that [result]
  • First-version boundary: list up to three essentials and what is explicitly not included
  • Definition of Done: a user can complete the main scenario from start to finish
2

Install Claude Code locally

10 min · one-time

This is a one-time setup per machine. After this, run claude inside the project folder.

node -v || brew install node
npm install -g @anthropic-ai/claude-code
claude --version
claude   # sign in via browser or set ANTHROPIC_API_KEY
3

Create the project and repository

5 min

A project folder plus git repository gives every change a history and makes deployment repeatable.

mkdir my-project && cd my-project
git init
claude
/init   # Claude scans the project and creates a starter CLAUDE.md
Create an empty GitHub repository now — you will connect and push it at step 13.
4

Create a local Python environment

5 min · Python projects

Keep project packages isolated from system Python. Create the environment before installing dependencies, and never commit it.

python3 -m venv .venv
source .venv/bin/activate
python -m pip install --upgrade pip
printf ".venv/\n__pycache__/\n" >> .gitignore
Skip this only when the project does not use Python. Use python -m pip so packages go into the active environment.
5

Add project instructions to CLAUDE.md

5 min

Give Claude only the project facts it cannot infer from code: commands, conventions, verification rules, and repository etiquette.

## Project
Build: [build command]
Test: [test command]

## Workflow
Write failing tests before production code.
Run checks before committing.
  • Keep the root file short and current
  • Put specialised instructions in .claude/skills/, not in one giant file
6

Add hooks for non-negotiable safeguards

5 min

Instructions are advisory; hooks enforce actions automatically. Use them only where a missed action has real cost.

Write a PreToolUse hook that blocks destructive commands.

Write a PostToolUse hook that reminds Claude to run
the relevant checks after editing files.
  • Block destructive operations such as rm -rf
  • Do not use hooks to block the normal fast push-to-main workflow
7

Turn the idea into a plan

Plan mode

Do not ask Claude to write code yet. Ask for the smallest approach, assumptions, risks, and a step-by-step plan you can correct first.

# Shift+Tab turns on Plan mode
I want to build: [idea from step 1].
What is the smallest approach? State assumptions and risks,
then create a step-by-step plan before writing any code.
8

Preserve context before switching tasks

Context

Keep one focused task per Claude session. Before switching topics or clearing context, save the working state so no decisions are lost.

Dump the current plan, decisions, and next action to PROGRESS.md.
/clear
Read PROGRESS.md and continue from where we left off.
  • Use one task per session
  • Update PROGRESS.md before /clear or a context switch
9

Define behavior and write failing tests first

Test-first

Tests written after implementation often mirror the code and stay green even when product behavior is wrong. Define observable behavior first, then prove tests fail because it is absent.

Before changing production code:
1. Restate acceptance criteria as user-visible behavior.
2. Write tests for that behavior and realistic edge cases.
3. Run them and show they fail for the right reason.
4. Only then implement the smallest change to pass them.
  • Test UI, API responses, CLI output, or other observable behavior — not private implementation details
  • A test must fail if the feature is removed or broken
10

Implement the smallest change

Implement

Implement only what makes the approved failing tests pass. Run the relevant tests after each small change and fix failures before moving on.

Implement the approved plan against the failing tests.
Run the relevant test suite after each change.
When tests pass, refactor only if they stay green.
11

Check the main scenario yourself

QA · 5 min

Automated checks are necessary but not sufficient. Open the result and use it as a real person would.

  • Complete the main user scenario manually
  • Check browser console or application logs for errors
  • Check mobile layout for web apps
  • Confirm the Definition of Done from step 1
12

Run an automated final review

Automation

Move repeatable review work out of the interactive session. Review the staged diff before committing, especially for unwanted edits and secrets.

git diff --staged
claude -p "review the staged diff and list risks, unexpected changes, and secrets" --output-format text
13

Commit and push to GitHub

Commit

This personal repository is speed-first: review the diff, run checks, then commit and push directly to main. Never force-push.

git add -A
git commit -m "Describe the change"
git remote add origin https://github.com/USER/REPO.git
git push -u origin main
14

Deploy and check the live link

Deploy

GitHub Actions validates the site first, then deploys GitHub Pages only if validation passes.

# Settings → Pages → Source: GitHub Actions
# Actions → Validate and Deploy GitHub Pages → wait for green
# https://USER.github.io/REPO/
To redeploy the current version without a new commit: Actions → Validate and Deploy GitHub Pages → Run workflow.
