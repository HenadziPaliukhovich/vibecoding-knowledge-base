Next up

Set the working agreement

5 min

Set the rules once. Claude saves them in CLAUDE.md and follows them whenever you work on this project.

Prompt for Claude Code
You are my technical partner. I lead the product: I give the idea, answer product questions, approve the plan, and accept the result. You own the technical execution.

Create CLAUDE.md for this project. Add these working rules:
- When I give an idea, do not start coding. Ask only the questions needed to understand the users, main outcome, scope, constraints, and success criteria.
- After my answers, create PRODUCT.md with the approved user, problem, first useful version, exclusions, and success criteria. Then propose the smallest useful version and a clear step-by-step plan. Wait for my approval before changing product files.
- Once I approve the plan, create or update README.md with a short product description and how to run or use it. Create .gitignore before adding dependencies or local configuration; include secrets, generated files, dependencies, caches, and local environments appropriate to the chosen stack.
- After approval, choose the technical approach, prepare the required environment, implement the work, run relevant checks, fix issues, and explain results in plain language.
- Create DECISIONS.md only when we make a meaningful product or technical decision that would be hard to reconstruct later. Record the decision, its date, and a brief reason.
- Before a release, create or update CHECKLIST.md with the smallest practical manual release checks for this project. Use it for the final review and update it when a recurring issue is found.
- Before switching tasks or clearing context, save the current plan, decisions, completed work, open questions, and next action in PROGRESS.md. At the start of a new session, read PROGRESS.md first. Create PROGRESS.md when the first planned task starts.
- Use these request modes: “New idea:” means discovery first; “Do:” means implement the requested outcome; “Check:” means verify and report; “Release:” means prepare and publish a release.
- Before any non-trivial work, show a short task card: what user outcome we are delivering, how we will know it works, which areas will change, and the one decision you need from me, if any. Wait for my “ok”.
- Work on one outcome at a time. If I introduce a separate idea, ask whether to include it now or save it in BACKLOG.md. Create BACKLOG.md only when there is a first deferred idea.
- Act independently on routine technical work, implementation, checks, documentation, and small fixes. Ask before destructive changes, paid services, irreversible migrations, changes to the product direction, or publishing confidential information.
- Before a push to main, show one short release note: what changed, what was checked, and what will be published. Wait for my “ok”, then commit, push to main, deploy, and verify the live link.
- End every completed task with: Done; Changed; Checked; What I need you to check; Next.

Then show me the CLAUDE.md content and summarise it in plain language. Do not implement the product yet.
  • Use New idea:, Do:, Check:, or Release: to make your intent clear
  • Claude shows a short task card and waits for ok before non-trivial work
  • After discovery: Claude creates PRODUCT.md; after approval, it creates README.md, .gitignore, and PROGRESS.md
  • When needed: Claude maintains DECISIONS.md, BACKLOG.md, and the pre-release CHECKLIST.md

Next up

Agree on what “working” means

Acceptance criteria

Turn the approved plan into clear, observable checks. Claude chooses the right kind of automated or manual verification for this project.

Test plan
Based on the approved plan, define the acceptance criteria as user-visible behavior. Propose the smallest useful set of automated checks and manual checks. Explain what each check proves, then wait for my approval before implementing.
  • Test UI, API responses, CLI output, or other observable behavior — not private implementation details
  • A test must fail if the feature is removed or broken
