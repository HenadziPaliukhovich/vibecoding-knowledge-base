Ключевые концепции

  • Vibe coding — разработка через промпты, без погружения в исходный код; термин ввёл Андрей Карпаты в феврале 2025.
  • Ты = менеджер, AI = активный джуниор. Много энергии, но нет понимания контекста без чёткого направления.
  • Гибридный подход: не полный vibe coding, а с проверкой и частичным погружением в реализацию.
  • Дефекты при таком подходе — математически неизбежны. Тестирование обязательная часть процесса.
  • Кодер vs инженер: кодер реализует готовое ТЗ; инженер отвечает за постановку задачи и контроль качества.

До того как дать задачу AI

Планирование
  • Пиши acceptance criteria до генерации кода.
  • Проси у модели сначала план, не сразу имплементацию.
  • Разбивай задачу на маленькие тестируемые подзадачи.

Во время генерации кода

Процесс
  • Начинай новый чат при смене темы или после долгого диалога.
  • Меняй одну вещь за раз и коммить после каждого шага.
  • Не давай той же модели писать тесты для её же кода.

QA-подход к AI-коду

Проверка
  • Гоняй SAST/dependency-аудит на каждый AI-коммит.
  • Проверяй auth-границы отдельно.
  • Тестируй API-контракты и обработку ошибок.
  • Веди трассировку требование → реализация → тест-кейс.
  • Делай exploratory-тестирование edge cases.
  • Помечай фичи тегом: человек / AI-assisted / полностью AI.

Риск-фокус

Приоритеты
  • Сначала деньги, комплаенс, целостность данных.
  • Гоняй регресс на каждое значимое AI-изменение, а не только перед релизом.

Пример CLAUDE.md

Файл-инструкция для AI-агента.

# CLAUDE.md

## Project Overview
Краткое описание проекта: что делает приложение, основной стек.

## Tech Stack
- Language: TypeScript / Node.js
- Framework: Express / React
- DB: MongoDB
- Tests: Jest + Supertest

## Rules for the AI agent
1. Never modify files in /migrations without explicit confirmation.
2. Always write or update tests for any new function or endpoint.
3. Do not introduce new dependencies without asking first.
4. Follow existing code style. Run lint before finishing a task.
5. Keep functions small and single-purpose (max ~40 lines).
6. Never remove existing tests to make a build pass — fix the code instead.

## Definition of Done
- [ ] Code compiles / builds without errors
- [ ] Unit tests written and passing
- [ ] No new lint warnings
- [ ] Edge cases considered (empty input, auth boundaries, invalid data)
- [ ] Short summary of changes provided

## Testing conventions
- Unit tests: co-located as *.test.ts
- Integration tests: /tests/integration
- Use existing fixtures in /tests/fixtures

## What NOT to do
- Do not silently swallow errors
- Do not disable existing security checks to "make it work"
- Do not commit directly to main — always use a feature branch

Шаблоны промптов

Планирование задачи

Прежде чем писать код, опиши план реализации:
1. Какие файлы будут изменены/созданы
2. Какие есть риски / edge cases
3. Как ты будешь это тестировать
Не пиши код, пока я не подтвержу план.

Ревью безопасности

Проверь этот код на:
- SQL/NoSQL injection
- отсутствие проверки авторизации
- утечку секретов/токенов в логах
- некорректную обработку ошибок
Дай список найденных проблем с указанием строк.

Тесты другой моделью

Вот код (без контекста, кто его писал).
Напиши unit-тесты, покрывающие happy path, граничные значения, невалидный ввод, ошибки.
Не предполагай, что реализация верна.
💡 Совет: держи эти промпты в снипетах (VS Code / Alfred / Raycast).
