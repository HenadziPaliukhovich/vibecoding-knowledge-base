Next up

Set the working agreement

5 min

Set the rules once. Claude saves them in CLAUDE.md and follows them whenever you work on this project.

Prompt for Claude Code
You are my technical partner. I lead the product: I give the idea, answer product questions, approve the plan, and accept the result. You own the technical execution.

Create CLAUDE.md for this project. Add these working rules:
- When I give an idea, do not start coding. Ask only the questions needed to understand the users, main outcome, scope, constraints, and success criteria.
- After my answers, create PRODUCT.md with the approved user, problem, first useful version, exclusions, and success criteria. Then propose the smallest useful version and a clear step-by-step plan. Wait for my approval before changing product files.
- Once I approve the plan, create or update README.md with a short product description and how to run or use it. Create .gitignore before adding dependencies or local configuration; include secrets, generated files, dependencies, caches, and local environments appropriate to the chosen stack.
- Never write API keys, tokens, or passwords directly in code. Store them in a local .env file (or equivalent) excluded by .gitignore, and read them from environment variables. Before configuring the live environment in the release step, tell me exactly which secrets need to be set there.
- Never run destructive or schema-changing operations against a production database. Use a local or staging database for development, and ask before any migration or operation that touches real production data. Before any production migration, confirm a recent backup exists.
- After approval, choose the technical approach, prepare the required environment, implement the work, run relevant checks, fix issues, and explain results in plain language.
- Create DECISIONS.md only when we make a meaningful product or technical decision that would be hard to reconstruct later. Record the decision, its date, and a brief reason.
- Before a release, create or update CHECKLIST.md with the smallest practical manual release checks for this project. Use it for the final review and update it when a recurring issue is found.
- Before switching tasks or clearing context, save the current plan, decisions, completed work, open questions, and next action in PROGRESS.md. At the start of a new session, read PROGRESS.md first. Create PROGRESS.md when the first planned task starts.
- Before any non-trivial work, show a short task card: what user outcome we are delivering, how we will know it works, which areas will change, and the one decision you need from me, if any. Wait for my “ok”.
- Work on one outcome at a time. If I introduce a separate idea, ask whether to include it now or save it in BACKLOG.md. Create BACKLOG.md only when there is a first deferred idea.
- Act independently on routine technical work, implementation, checks, documentation, and small fixes. Ask before destructive changes, paid services, irreversible migrations, changes to the product direction, or publishing confidential information.
- Before a push to main, show one short release note: what changed, what was checked, and what will be published. Wait for my “ok”, then commit, push to main, deploy, and verify the live link.
- End every completed task with: Done; Changed; Checked; What I need you to check; Next.

Then show me the CLAUDE.md content and summarise it in plain language. Do not implement the product yet.
  • Keep CLAUDE.md concise and under 150 lines so rules are never ignored
  • Claude shows a short task card and waits for ok before non-trivial work
  • After discovery: Claude creates PRODUCT.md; after approval, it creates README.md, .gitignore, and PROGRESS.md
  • When needed: Claude maintains DECISIONS.md, BACKLOG.md, and the pre-release CHECKLIST.md

Give Claude your idea

Discovery

Describe the product in your own words. Claude clarifies what you need, then gives you a plan to approve — it does not guess and start coding.

Prompt
Here is my idea: [describe it in your own words].

Follow the project instructions. First ask only the questions you need to understand the goal, users, main scenario, scope, and success criteria. Do not make changes yet. If my idea bundles more than one outcome, tell me so we can tackle them one at a time.

After I answer, give me the smallest useful version and a step-by-step plan for approval.
Pro-tip: Press Shift+Tab in terminal to toggle Claude Code Plan Mode so Claude cannot touch files until you approve.

Next up

Agree on what “working” means

Acceptance criteria

Turn the approved plan into clear, observable checks. Claude chooses the right kind of automated or manual verification for this project.

Test plan
Based on the approved plan, define the acceptance criteria as user-visible behavior. Propose the smallest useful set of automated checks and manual checks. Explain what each check proves, then wait for my approval before implementing.
  • Test UI, API responses, CLI output, or other observable behavior — not private implementation details
  • A test must fail if the feature is removed or broken
  • If the project has logins or private data: confirm protected pages and API routes reject unauthenticated access
  • If the project accepts user input: confirm it is validated on the server, not only in the interface
  • If different users share the app: confirm one user cannot read or change another user’s data

Next up

Implement the smallest change

Implement

Implement only what makes the approved failing tests pass. Run the relevant tests after each small change and fix failures before moving on.

Prompt
Implement the approved plan against the failing tests.
Run the relevant test suite after each change.
When tests pass, refactor only if they stay green.
If you add a new dependency, confirm it installs and imports cleanly before relying on it.
After each change, explain in two or three plain-language sentences what the code now does.
Context tip: If the session gets long or sluggish, ask Claude to update PROGRESS.md, type /clear, and continue with a fresh context.

Next up

Check the main scenario yourself

QA · 5 min

Automated checks are necessary but not sufficient. Starting without errors is not the same as working — open the result and use it as a real person would.

  • Complete the main user scenario manually
  • Try an empty field, an invalid value, and a mid-action network drop — not just the happy path
  • Check relevant logs or error output (and browser console for web apps)
  • For web apps: check responsive and mobile layout
  • Confirm the Definition of Done from step 3

Commit and push your project

Commit

This repository is speed-first: review the diff, run checks, then commit and push directly to main. Never force-push.

Prompt for Claude Code
Review the current changes, then stage, commit, and push them directly to main on the remote repository. Never force-push.

Write a clear, short commit message describing what changed and why. If no remote is configured yet, set it up first, then push.

Next up

Run in the real environment

Release

A project is only finished when it runs where you actually need it. Let Claude configure and verify the target run environment for your stack.

Prompt for Claude Code
The core changes are committed. Propose the simplest way to run or publish this project so I can use it end-to-end (e.g. GitHub Pages or Vercel for web, server or daemon for Python, or a global command for CLI).

Explain what needs to happen in plain language, handle the configuration yourself, and give me the command or link to test it. If any secrets from .env are needed in the live environment, tell me exactly which ones to set there — never commit them.

Also tell me the simplest way to roll back to the previous working version if something breaks after this release, in case I need it.
  • Web: verify the public link on desktop and mobile
  • CLI: run the installed command from any directory with real inputs
  • Python / Backend: verify the service or bot starts cleanly and responds
  • Confirm you know the rollback step before moving on
