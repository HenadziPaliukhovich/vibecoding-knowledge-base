Local environment setup

01

Do this once on a new machine. After that, it is just running claude inside the project folder.

01

Install Node.js and the Claude Code CLI

Claude Code is a Node package, installed globally through npm.

node -v || brew install node
npm install -g @anthropic-ai/claude-code
claude --version
02

Authenticate

Use either a Claude account (Pro/Max) or an Anthropic API key.

claude
# interactive mode will open a browser sign-in link
# or set an environment variable instead:
export ANTHROPIC_API_KEY="sk-ant-..."
03

Install helper CLIs

Claude works better with external services through their official CLIs than through hand-written API flows.

brew install gh          # GitHub
gh auth login
brew install awscli       # if you use AWS
brew install google-cloud-sdk   # if you use GCP
04

Initialize the project

The /init command scans the repository structure and creates a starter CLAUDE.md, which you should then trim and refine manually.

cd my-project
claude
/init
/context   # verify that CLAUDE.md was actually loaded
05

Access modes and sandbox

Claude Code has three execution modes — choose based on the task's risk level, not one mode for everything.

  • Plan mode — inspect and refine, nothing changes
  • Manual approvals — confirm each Edit and Bash action
  • Auto-accept — safe actions move faster, but only in an isolated environment
/permissions
# add to allowlist: npm run lint, npm test, git commit *, git diff
/sandbox   # enable filesystem and network isolation
/model     # switch the model for the task
06

Personal settings vs team settings

Three memory layers help you avoid mixing personal habits, team rules, and local scratch notes.

  • ./CLAUDE.md — shared project rules, committed to git
  • ./CLAUDE.local.md — your temporary notes, kept in .gitignore
  • ~/.claude/CLAUDE.md — global personal rules for all projects
07

Lock down the local environment

It is better to work in a reproducible environment: matching Node, Python, and system CLI versions give both you and Claude more predictable results.

# .devcontainer/devcontainer.json
{
  "image": "node:20",
  "postCreateCommand": "npm install -g @anthropic-ai/claude-code && npm ci",
  "remoteEnv": { "ANTHROPIC_API_KEY": "${localEnv:ANTHROPIC_API_KEY}" }
}

# quick isolated run through Docker
docker run --rm -it -v $(pwd):/work -w /work node:20 bash -lc \
  "npm install -g @anthropic-ai/claude-code && claude"

Working cycle: 4 phases

02

The main mistake is letting Claude write code immediately. Split research, planning, and implementation, or you risk solving the wrong problem well.

1

Explore — plan mode

Press Shift+Tab until the status says "plan mode on". Claude reads code and answers questions without changing anything.

read /src/auth and understand how we handle sessions and login.
also look at how we manage environment variables for secrets.
2

Plan — ask for a detailed plan

You can open the plan in the editor with Ctrl+G and annotate it manually: "use PATCH, not PUT", "add created_at with NOW()".

I want to add Google OAuth. What files need to change?
What's the session flow? Create a plan.

# after editing the plan:
address all notes, don't implement yet
3

Implement — with verification

Leave plan mode and give Claude a success criterion: tests, a script, or a screenshot.

implement the OAuth flow from your plan. write tests for the
callback handler, run the test suite and fix any failures.
4

Commit — with description

Do not leave commit messages for later — ask for them immediately.

commit with a descriptive message and open a PR

Verification loop

The key Anthropic-style rule: do not ask "build it", ask "build it and verify it". A test, build, screenshot diff, or explicit acceptance check turns Claude from a text generator into an executor with a clear stopping condition.

implement the change, run tests, fix failures,
and summarize what you verified before stopping.

Checkpoint and rollback

If Claude goes in the wrong direction, do not argue for 20 messages in a row. Use a quick rollback to an earlier checkpoint, or clear the session and re-enter with a sharper prompt.

Esc Esc      # open checkpoints
/rewind      # return to an earlier state
/clear       # start a fresh session for another task

When plan mode is overkill

If a change fits in one sentence (a typo, a log line, a variable rename), a plan is unnecessary — ask Claude to do it directly. A plan is worth it when the approach is unclear, multiple files will change, or you do not know the codebase well.

How to write CLAUDE.md

03

CLAUDE.md is read at the beginning of every session. Claude Code's system prompt already consumes part of the instruction-following budget, so an oversized file means important rules get lost in the noise.

✓ Include

Bash commands Claude will not guess; code style that differs from the default; test instructions; repo etiquette (branches, PRs); architectural decisions; environment variables; non-obvious project specifics

✗ Exclude

Anything Claude can infer from the code; standard language conventions; detailed API docs (link them instead); frequently changing information; long explanations and tutorials; file-by-file codebase descriptions

Example of a short root file (real structure)

# CLAUDE.md

## Project
Monorepo managed with pnpm workspaces. Packages in packages/*.
Build: pnpm build. Test: pnpm test.

## Code style
- Use ES modules (import/export), not CommonJS (require)
- Destructure imports when possible: import { foo } from 'bar'

## Workflow
- Typecheck after a series of changes: pnpm typecheck
- Prefer running single tests, not the whole suite, for speed
- Use the simplest possible approach — no premature abstractions

## For domain-specific rules, see:
- Payments: read docs/payment-architecture.md first
- API conventions: src/api/CLAUDE.md

Progressive disclosure

Do not paste a full document into CLAUDE.md — it burns instruction budget in every session. Instead, link to a file Claude will read only when needed.

## Payments
When touching src/payments/, first read
docs/payment-architecture.md before editing.

Scoped files by subfolder

Claude loads CLAUDE.md files from the current working directory upward to the repo root. You can keep database or API rules locally, so they activate only in the relevant area.

src/persistence/CLAUDE.md   → database rules
src/api/CLAUDE.md           → endpoint conventions
~/.claude/CLAUDE.md         → your personal global rules

Diagnostics

If Claude ignores a rule, the file is probably too long and the rule is lost in the noise — shorten it. If Claude keeps asking about something already in the file, the wording is ambiguous. If a rule is consistently skipped, mark it with a single word like "IMPORTANT", but do not mark too many lines or nothing will stand out. Keep the file in git so the team can improve it, and run /doctor for automatic suggestions on trimming it down.

Context management

04

Response quality starts dropping long before the window is full — many practitioners try not to exceed roughly 60% by feel. Auto-compaction usually kicks in around 83% and loses detail.

Document & Clear — the base pattern

As soon as context starts to feel heavy, dump the plan and progress to markdown, clear the session, and restart by reading that file. This way, you decide what survives the reset instead of auto-compaction deciding for you.

# save progress before clearing
Dump current plan and progress to PROGRESS.md,
including decisions made and files touched.

/clear

# new session
Read PROGRESS.md and continue from where we left off.

One task — one session

A "trash session" starts with one task, drifts into unrelated questions, then tries to come back — the context is now full of irrelevant matter. After two failed fixes for the same problem, clear the session and rephrase the prompt instead of continuing the argument.

  • /clear between unrelated tasks
  • /compact Focus on the API changes for targeted compression
  • /btw for side questions that should not grow the main context

Subagents for investigation

Code research may read dozens of files — all of that volume eats the main context. A subagent works in a separate window and returns only a summary.

Use subagents to investigate how our authentication system handles
token refresh, and whether we have any existing OAuth utilities I should reuse.

Hooks and result verification

05

CLAUDE.md is advisory — it is not always followed. Hooks are deterministic scripts that guarantee an action every single time, with no exceptions.

Auto-format after edits

A PostToolUse hook runs Prettier or a linter right after Edit/Write, without interrupting Claude's flow.

{
  "hooks": {
    "PostToolUse": [{
      "matcher": "Edit|Write",
      "hooks": [{
        "type": "command",
        "command": "prettier --write \"$CLAUDE_FILE_PATHS\""
      }]
    }]
  }
}

Hard blocking for dangerous commands

A PreToolUse hook with exit code 2 blocks the action entirely — for example, pushing to main or running rm -rf.

Write a hook that blocks 'git push' directly to main
and suggests opening a PR instead.

Write a hook that blocks 'rm -rf' and suggests 'trash' instead.

Give Claude a way to check itself

Without a verifiable criterion, "looks done" becomes the only signal, and you become the test loop yourself. Give it a test, a build, or a screenshot to compare against.

BeforeAfter
implement a function that validates email addresseswrite a validateEmail function. example test cases: user@example.com is true, invalid is false. run the tests after implementing
make the dashboard look better[screenshot] implement this design. take a screenshot of the result and compare it to the original. list differences and fix them
the build is failingthe build fails with this error: [text]. fix it and verify the build succeeds. address the root cause, don't suppress the error

Adversarial review — a second opinion

A fresh subagent sees only the diff and the criterion, not the reasoning history — so it judges the result more honestly.

Use a subagent to review the rate limiter diff against PLAN.md. Check that
every requirement is implemented, listed edge cases have tests, and nothing
outside the task's scope changed. Report gaps, not style preferences.

What to steer with what

06

Not everything belongs in one CLAUDE.md. A solid working environment is built from soft rules, hard constraints, and on-demand context.

ToolWhen to use itWhat to store
CLAUDE.mdFor short rules needed in almost every sessionworkflow, style, commands, verification criteria
HooksWhen a rule must be enforced every timeformatting, blocking pushes to main, banning dangerous commands
SkillsWhen the knowledge is only needed for a specific taskdeploy, migrations, release, performance review
SubagentsWhen you need isolated research or reviewauth audit, security review, diff review, docs pass

How to keep CLAUDE.md short

Write only what the model cannot infer from the code. A good rule is testable, brief, and, when it forbids something, immediately suggests the safe alternative.

Bad: don't use destructive commands.
Good: never run rm -rf; move files to Trash or ask first.

Skills instead of long walls of text

Move rare, bulky instructions into .claude/skills/. Then the root CLAUDE.md stays compact, and Claude reads the detailed playbook only when needed.

.claude/
  skills/
    deploy/SKILL.md
    db-migrations/SKILL.md
    code-review/SKILL.md

Automation and scale

07

Once the base loop works, move repeatable work into headless commands, batch mode, and separate review sessions.

Headless and CI

For repeatable work, non-interactive runs are more convenient. This fits generating summaries, checking diffs, migrating a series of files, and CI tasks.

claude -p "review the staged diff and list risks" \
  --output-format text

claude -p "summarize changes in this PR" \
  --output-format json

Fan-out and writer/reviewer

One session writes, another reviews from scratch. For a series of similar files, it is often more efficient to run Claude in a loop or a batch flow with a narrow prompt scope.

for file in $(cat files.txt); do
  claude -p "migrate $file to the new API and report OK or FAIL"
done

Prompt library

08

TDD loop

1. Write tests for the auth module using pytest.
TDD approach, no mock implementations.
2. Run the tests — they should all fail.
3. Commit the failing tests as a checkpoint.
4. Write the implementation. Do not modify
the tests. Keep going until all tests pass.

Interview before the feature

I want to build [description]. Interview me in detail
using the AskUserQuestion tool. Ask about technical
implementation, UI/UX, edge cases, and tradeoffs.
Don't ask obvious questions. Keep interviewing until
we've covered everything, then write a spec to SPEC.md.

Bug investigation

Users report that login fails after session timeout.
Check the auth flow in src/auth/, especially token
refresh. Write a failing test that reproduces the
issue, then fix it.

Autonomous batch mode

for file in $(cat files.txt); do
  claude -p "Migrate $file from Python 2 to Python 3.
  Return OK or FAIL." \
    --allowedTools "Edit,Bash(git commit *)"
done

Writer / Reviewer

# Session A
Implement a rate limiter for our API endpoints

# Session B (fresh context)
Review the rate limiter in @src/middleware/rateLimiter.ts.
Look for edge cases, race conditions, and consistency
with existing middleware patterns.

Learning a third-party CLI

Use 'foo-cli-tool --help' to learn about foo tool,
then use it to solve A, B, C.

This form is only convenient as a draft in the current browser. Anything you truly want to keep across machines or after a new deploy should live in the repository as a file.

Durable notes — only through git

Keep personal playbook notes in artifacts/notes/, and project rules in CLAUDE.md or .claude/skills/. That way, the knowledge survives a new machine, a cleared browser, and any redeploy.

mkdir -p artifacts/notes
cat > artifacts/notes/debugging-session.md <<'EOF'
# Debugging session
- Symptom:
- Root cause:
- Fix:
- Verification:
EOF

git add artifacts/notes/debugging-session.md
git commit -m "Add debugging note"
git push
