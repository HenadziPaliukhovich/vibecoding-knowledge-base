## Rules

1. Read existing code and tests before editing.
2. Ask before adding a dependency or changing a public API.
3. Make one logical change at a time.
4. Add or update tests for changed behavior.
5. Never remove tests or security checks to make the build pass.
6. Never expose credentials, tokens, personal data, or secrets in logs.

## Testing (mandatory)

- Every new or changed function, component, and user-facing flow must have at least one test covering the happy path, one failure/edge case, and one boundary condition.
- Skipping tests is only allowed for pure copy/content changes with zero logic.
- "It works" means it has a passing test, not "I ran it once and it didn't crash."

## Deployment (must be reproducible)

- Run/deploy steps must be a single reproducible command: a `Dockerfile`/`docker-compose.yml`, or a pinned lockfile (`package-lock.json`, `requirements.txt` with exact versions). "Install Node 18, then npm install, then..." is not an acceptable deployment description.
- Verify the actual deployed environment after release, not only the local dev run.

## Documentation (examples over prose)

- Any README/guide must lead with at least one copy-pasteable working example. Prefer a short doc with 2-3 working examples over a long one with diagrams and no runnable snippet.

## Code style (avoid an AI-generated look)

- Never mention Claude, AI, or the generation process in code, comments, or commit messages (no "Generated by Claude", "As an AI...", "Here's the implementation...").
- No comments that narrate the obvious (`// increment counter` above `i++`). Comment only *why*, not *what*, and only where the reason isn't obvious from the code.
- Match the existing file's naming, indentation, and quote-style conventions exactly; don't mix conventions mid-file.
- Do not add defensive code, extra abstraction layers, or config options for cases the task didn't ask for. Write the smallest solution that satisfies the acceptance criteria.
- Avoid boilerplate docstrings/JSDoc on trivial, self-explanatory functions.
- Do not leave placeholder comments (`// TODO: implement`) or stub functions unless scaffolding was explicitly requested.
- Remove debug artifacts before committing: stray `console.log`/`print`, commented-out code, unused imports.
- Vary structure the way a human iterating on a real codebase would; not every function needs an identical shape or identical variable names (`data`, `result`, `item`).
- Prefer terser code over verbose, over-explained code — exhaustive commentary is the most common AI tell.

## Commit messages (avoid AI traces)

- Write commit messages as if a human typed them directly: short, factual, imperative ("Fix off-by-one in pagination", not "I have successfully implemented...").
- Never add `Co-Authored-By: Claude`, `Generated with Claude Code`, robot emoji, or any AI/tool attribution trailer.
- No narrated session summaries or restated diffs in the commit body — one or two lines of *what* and *why* is enough.
- If history already contains AI traces, use `artifacts/prompts/clean-ai-traces-from-history.sh` to rewrite it (destructive: creates a backup branch, requires `--force-with-lease` push).

## Suggested hooks (`.claude/settings.json`)

Copy these into a new project's hooks (adjust commands to the stack) to enforce testing and lint/format automatically before every `git commit`, instead of relying on memory:

- A `PreToolUse` hook on `Bash` that blocks `git commit` when staged logic files have no corresponding staged test file.
- A `PreToolUse` hook on `Bash` that runs the project's linter and formatter (e.g. ESLint + Prettier via `npx`, or `ruff` for Python) against staged files and blocks the commit on failure.

See this repository's `.claude/hooks/require_tests_before_commit.py` and `.claude/hooks/require_lint_and_format_before_commit.py` for a working reference implementation.

## Definition of done

- [ ] Acceptance criteria met
- [ ] Tests added or updated, and passing
- [ ] Tests, lint, and build pass
- [ ] Errors and edge cases handled
- [ ] Run/deploy steps are a single reproducible command; deployed result checked
- [ ] Any new/updated README leads with a working example
- [ ] Code and commit messages contain no AI/Claude traces
- [ ] Short change summary provided
